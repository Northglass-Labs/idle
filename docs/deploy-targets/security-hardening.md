# Security baseline for a self-hosted Idle relay

This checklist is for an internet-facing Linux host running the relay behind a
reverse proxy. Managed platforms cover some of these controls, but the same
principles apply.

Before changing SSH, firewall, or TLS configuration, take a provider snapshot,
keep the current administrative session open, and confirm you have a recovery
console. Commands vary by distribution; inspect each command before running it.

## Network boundary

- Bind the bare-metal relay to `127.0.0.1:3005` and expose it through a reverse
  proxy. Containers bind internally to `0.0.0.0`; publish that port only to the
  intended host interface or platform ingress.
- Permit inbound SSH only from trusted source networks when practical. Permit
  public HTTP only when required for redirect or certificate validation, and
  serve application traffic over HTTPS.
- Keep PGlite files, metrics, debug endpoints, container daemons, and provider
  dashboards off the public network.
- Configure a default-deny virtual host so unknown `Host` headers do not reach
  the relay.

A minimal UFW policy for a host that terminates HTTP and HTTPS locally is:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
sudo ufw status verbose
```

Adjust this for your provider firewall and administration network before
enabling it.

## TLS and reverse proxy

- Use a publicly trusted certificate for the exact relay hostname and automate
  renewal.
- Forward WebSocket upgrade headers and preserve the original scheme and host.
- Reject unrecognized hostnames rather than serving the first configured site.
- Set request-body and timeout limits appropriate for Idle attachments and
  long-lived Socket.IO connections.
- Add HSTS only after HTTPS is reliable. Do not add `includeSubDomains` or
  `preload` unless every affected subdomain can make that long-term commitment.

For a separately hosted web app, set at least `X-Content-Type-Options`, a strict
`Referrer-Policy`, clickjacking protection, and a tested Content Security Policy.
Do not copy a generic CSP or Permissions Policy without exercising login,
pairing, microphone, camera, WebSocket, and attachment flows; an overbroad
policy can silently disable supported features.

## SSH and host access

Use a dedicated non-root account, key-based authentication, least-privilege
sudo rules, and provider audit logs. Prefer an SSH configuration drop-in over
editing the distribution file in place:

```text
# /etc/ssh/sshd_config.d/99-idle-hardening.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

Validate before reload:

```bash
sudo sshd -t
```

Open a second key-authenticated session before closing the first. Add rate
limiting such as fail2ban only after confirming its rules will not block your
administration path.

## Secrets, storage, and logs

- Keep the application image root read-only. Runtime code and static web assets
  should remain root-owned and non-writable by the service user. Mount only the
  documented writable paths: persistent `/data` and ephemeral `/tmp`.
- Store `IDLE_MASTER_SECRET` in a password manager and inject it through the
  runtime secret store. Do not place it in Git, images, unit files, shell
  history, process arguments, or support bundles.
- Restrict `/data` and environment files to the service account. Back up the
  data volume and master secret as one recovery set.
- Redact tokens, session identifiers, pairing material, message content, local
  paths, hostnames, and IP addresses from logs before sharing them.
- Apply operating-system and container-image security updates on a regular
  schedule. Restart after kernel or runtime updates when required.

## Verification

Run these checks from a network outside the host:

```bash
curl --fail --silent --show-error https://relay.example.com/health
curl --silent --show-error --head https://relay.example.com/
nmap -Pn -p 22,80,443,3005,5432,6379,9090 <public-ip>
```

Only the ports you intentionally exposed should be reachable. Also verify:

- an unknown `Host` header is rejected;
- password SSH authentication fails while key authentication succeeds;
- certificate renewal has a successful dry run;
- a paired session survives a restart;
- a restore into an isolated host can read the backed-up state;
- logs generated by pairing and messaging contain no secret or message body.
- the service user cannot write the relay bundle, Prisma schema, or static web
  document root.
